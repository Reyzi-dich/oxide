# Архитектурные решения и философия проекта 'Oxide'

Этот документ поясняет, *почему* кодовая база Oxide устроена именно так,
какие инженерные решения в ней приняты и как они работают на практике.

Проект проектируеться с принципом полной прозрачности и нулевой элитарности, 
поэтому объясняться в нём будут даже "очевидные" по чьему то мнению вещи для разработки на расте.
Моя цель чтобы проект был не только чистым, но ещё и простым в изучение для начинающих разработчиков или новых контрибютеров.

---

## 1. Инкапсуляция: Приватные поля, геттеры и сеттеры.

### Вопрос
Зачем делать поля структур приватными и писать ручные геттеры/сеттеры, 
вместо того чтобы сделать все поля публичными (`pub`)?

### Концепция (Зачем это нужно абстрактно?)
В программировании есть понятие **Инварианта** - это правило, которое *всегда* 
должно выполняться для того, чтобы программа работала корректно.

Если дать стороннему коду прямой доступ к внутренностям структуры, этот код сможет 
случайно или намеренно нарушить инвариант, разрушив работу всей системы.

### Реальный пример из Oxide ([`oxide-runtime: Journal`](../crates/oxide-runtime/src/journal/journal.rs))
Внутри `Journal` мы используем кольцевой буфер `entries`(записи) и число `capacity` (вместимость).

- **Первый инвариант:** Вместимость журнала всегда должна быть больше 0 (`capacity > 0`).
- **Второй инвариант:** Записи должны добавляться строго хронологически в конец буфера.

#### Что произойдет с публичными полями (`pub capacity`, `pub entries`)?
Любой модуль сможет написать:
```rust
journal.capacity = 0;              // СЛОМАНО: Журнал больше не может хранить данные.
journal.entries.push_front(entry); // СЛОМАНО: Нарушен порядок времени (запись вставлена в начало).
```

#### Как нас защищают приватные поля и методы?

Сделав `entries` и `capacity` приватными, мы заставляем взаимодействовать с журналом
только через безопасные методы-врата:

- `set_capacity(new_capacity)` - проверяет, что new_capacity > 0, и сам вычищает старые записи,
если буфер урезали. Инвариант защищён.

- `push(entry)` - гарантирует, что запись попадает только в конец очереди (push_back),
сохраняя хронологию.

- Геттер `entries(&self)` - отдаёт данные только для чтения (&). Внешний код
может прочитать логи, но не может их стереть или подделать.
